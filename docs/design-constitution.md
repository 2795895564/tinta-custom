# Tinta 设计宪法

> 状态：`[提案]`（原则方向已确认，具体措辞仍可修订）
>
> **唯一职责**：不可违背的原则、关键不变量、模块职责边界。
> 产品目标/范围见 [product-brief.md](product-brief.md)；状态与命令见 [interaction-state-machine.md](interaction-state-machine.md)；
> 当前实现状态见 [dev-status.md](dev-status.md)。
>
> 本文的 `[已决定]` 表示规则已拍板，不代表代码已经做到；代码差距记录在 `dev-status.md`。

## 0. 一句话

`[已决定]` **Tinta 是一个安静、本地优先的 Markdown 工作区：文档是主角，键盘可预测，任何操作都不会丢东西。**

英文版本，方便放在 README：

> A calm, local-first Markdown workspace where the document is the hero, the keyboard is predictable, and nothing is lost.

## 1. 三个候选核心

`[已决定]` 采用 A + B + C 的合成；下面三个候选保留，用来说明每个核心排斥什么。

| 核心 | 它意味着什么 | 它排斥什么 |
| --- | --- | --- |
| **A. 安静阅读/写作** | 文档占主导，界面退后；默认设置经过打磨，减少弹窗和装饰 | 功能堆砌、常驻侧栏、过多提示 |
| **B. 本地优先** | 普通文件是事实源，设置/会话透明；不依赖云和私有数据库 | 云端锁定、隐藏状态、必须登录 |
| **C. 键盘优先的工作区** | 一个命令一个含义；焦点可预测；所有动作都能用键盘完成 | 隐藏模式、冲突快捷键、只能鼠标的操作 |

推荐的主核心是 **A + B + C 的合成**，但排序要明确：

1. 不丢数据（硬底线）
2. 文档优先
3. 可预测
4. 本地优先
5. 安静
6. 快
7. 可维护

当原则冲突时，序号靠前的赢。例如“加一个常驻面板会让功能更强大” vs “文档优先”——默认不加，除非它能证明自己不抢文档的空间。

## 2. 非目标（Non-goals）

明确不做什么，和明确做什么一样重要：

- 不是 IDE：不追求调试、重构、语言服务器。
- 不是完整文件管理器：仓库/目录是为 Markdown 工作流服务的，不承诺替代 Explorer。
- 不是云同步服务：可以有导出/分享，但不把云盘当事实源。
- 不是插件平台：先把核心做稳，再考虑扩展点。
- 不是 WYSIWYG 字处理器：Markdown 源码和渲染结果的关系是产品的核心，不是要隐藏的细节。
- 不为“功能数量”做设计；每个新功能必须证明它不破坏前三条原则。

## 3. 不变量（Invariants）

这些是硬约束，测试和代码评审都应该能检查。标记表示规则状态，不是代码状态（代码状态见 `dev-status.md`）：

1. `[已决定]` **Esc 永不退出软件。** 它只关闭最上面一层；退出只有 `Q`、窗口关闭、`Alt+F4`。
2. `[已决定]` **不丢数据。** 关闭、崩溃、切换仓库都不能静默丢文档；脏缓冲走保存询问或草稿恢复。
3. `[现状]` **当前文档只有一个槽位。** `app.root` / `app.currentFile` 永远是活动标签的文档；切标签是换入换出，不是复制。
4. `[已决定]` **首页标签固定在最左。** 打开文件不关闭它；它不可关闭、不可拖动、不能被“关闭其他/左右”带走（P1 后）。
5. `[现状]` **仓库根是墙。** 导航不能越出当前仓库根。
6. `[现状]` **不支持的文件不会被当成文档打开。** 支持的类型明确列在 `document.cpp`，其他显示为不可打开。
7. `[已决定]` **设置写失败必须可见。** 不允许静默吞掉 `saveSettings` 的失败。
8. `[提案]` **输入有唯一解析路径。** 键盘事件通过一个命令/焦点模型解析，不在多个分支里重复定义同一个动作。
9. `[提案]` **模态/浮层的优先级是确定的。** 同一时刻只有一个最上层接收 Esc/Enter。
10. `[现状]` **后台扫描不阻塞 UI。** 大仓库扫描、索引构建都在工作线程，过期结果丢弃。

## 4. 决策规则（Decision rules）

比原则更具体，用来快速裁决：

- **功能 vs 安静**：默认选安静；功能必须证明自己值得占用常驻空间。
- **速度 vs 正确性**：数据正确性优先；渲染流畅度优先于视觉完美。
- **键盘 vs 鼠标**：键盘优先，但每个动作都要有鼠标路径；不能有“只能键盘”的隐藏操作。
- **意见 vs 配置**：默认值要有主见；设置只暴露“用户能理解的真实取舍”，不暴露实现细节。
- **新模块 vs 扩展现有**：优先扩展现有契约；只有出现新的“被拥有的状态”或新的外部资源时才建新模块。
- **抽象 vs 重复**：同一模式重复到第三次再抽象；前两次允许局部重复，避免过早框架化。
- **即时模式 vs 控件树**：保持即时模式；需要复用的是状态和纯函数，不是控件对象。
- **纯逻辑 vs 薄壳**：业务规则进纯模块；Win32/D2D 只做接线和绘制。

## 5. 顶层分层

```text
┌─────────────────────────────────────────────┐
│ Vision / Constitution                       │
│ 为什么做、优先级、非目标、不变量              │
├─────────────────────────────────────────────┤
│ Domain Model                                │
│ 文档、标签、工作区、仓库、设置、索引          │
│ 实体、归属、生命周期、纯函数                  │
├─────────────────────────────────────────────┤
│ Interaction Model                           │
│ 命令、焦点栈、事件类型、Esc/Enter 规则         │
├─────────────────────────────────────────────┤
│ Presentation                                │
│ 视图、布局、主题、设计令牌、设置面板           │
├─────────────────────────────────────────────┤
│ Platform Shell                              │
│ Win32、Direct2D、文件对话框、线程             │
└─────────────────────────────────────────────┘
```

依赖规则：

- 上层可以依赖下层的**契约**，下层不能依赖上层的 UI。
- `domain` 尽量不包含 `windows.h`；需要平台能力时通过接口/effect 交给 shell。
- `presentation` 只读 domain，写操作通过 command/effect。
- `shell` 是唯一持有消息循环和 D2D 设备的地方。
- `App` 是组合根（composition root），不是业务层；不要把新规则继续堆进 `app.h`。

## 6. 设置界面：对模型细节的控制

你的直觉是对的：**设置界面就是模型细节的控制面。** 但要加一个约束：它控制的是**用户能理解的取舍**，不是实现细节。

### 6.1 三类状态要分开

| 类型 | 例子 | 放哪里 |
| --- | --- | --- |
| **偏好（Preference）** | 主题、语言、启动方式、编辑预览、快捷键 | `settings.ini` |
| **会话（Session）** | 打开的文件标签、活动标签、上次目录 | session / `lastDir` |
| **运行时（Runtime）** | 当前解析树、索引状态、悬浮选择 | 内存，不持久化 |

设置面板只编辑第一类。把 session 当设置、把运行时常量当设置，都会让面板越来越乱。

### 6.2 偏好 Schema

每个设置项是一个声明，而不是一段手写 UI：

| 字段 | 说明 |
| --- | --- |
| `id` | 稳定标识，如 `editor.showPreview` |
| `group` | Appearance / Editor / Reading / Workspace / Keys / Files / Advanced |
| `type` | bool / enum / int / string / chord |
| `default` | 默认值 |
| `scope` | global / window |
| `apply` | live / newWindow / restart |
| `validate` | 范围、枚举、冲突 |
| `labelKey` / `helpKey` | i18n |
| `advanced` | 是否收进高级区 |

设置面板是 schema 的**一个视图**：分组、控件、默认值、校验、应用时机都从表里来。加一个设置项应该是“加一行 schema + 一个控件类型”，而不是再改四处。

### 6.3 快捷键是偏好的子模型

快捷键不是普通字符串，而是：

```text
CommandId + Context + KeyChord + Profile + Override
```

设置界面捕获的是 **KeyChord**（可含 Ctrl/Shift），不是裸键；保存前做**冲突检测**（同一 context 同一 chord 不能绑两个命令）。`Esc`、快速跳转等固定键不出现在可编辑列表里，或者标记为“固定”。

### 6.4 设置面板的交互

- 编辑草稿 → Apply 校验并原子保存 → 取消回滚。
- 每个分组可“恢复默认”；每个项可单独重置。
- 搜索设置项（复用命令/快速跳转的模糊匹配）。
- 应用时机要标记：主题/语言/编辑预览可 live；启动方式、部分键位可以下次窗口生效。
- 写失败在面板底部显示路径和错误，不静默。

### 6.5 不建议做成设置的东西

- 内部缓存大小、扫描线程数、渲染批次大小（除非高级/诊断）。
- 本应由设计决定、用户不需要理解的视觉间距。
- 能让两个不变量互相冲突的开关（例如“Esc 退出”）。

## 7. 模块宪章（Module charters）

每个模块用三句话描述：**职责、契约、绝不做什么**。状态归属不在这里重复，见
[input-workspace-model.md](input-workspace-model.md) 的归属表。

| 模块 | 职责/契约 | 绝不 |
| --- | --- | --- |
| `markdown` 解析 | bytes → element tree + source offsets | 读写文件、碰 UI |
| `render` 布局/绘制 | tree + theme + width → 绘制 | 修改文档树 |
| `editor` | 编辑命令 → buffer 变化 + 保存请求 | 直接写文件、切标签 |
| `tabs` | open/close/activate/swap 文档 | 解析/排版/渲染 |
| `workspace`（现 `home_logic` + `dirmodel` + `repos`） | workspace 命令 → 状态 + effects | 绘制、弹窗 |
| `settings` | schema + load/save + validate | 拥有 session/运行时状态 |
| `commands` | context + chord → command | 执行具体行为 |
| `workspace_index` | repo scan → entries; pure query/ranking + generation | 绘制、读键、阻塞 UI |
| `overlays` | 浮层状态 | 绘制 + 命中 + 优先级 | 拥有仓库/文档数据 |

### 文档流水线和 UI 不是同一种抽象

不要强行让 parser/renderer/editor 都套进“屏幕/命令”模型：

- parser 是**纯函数**；
- layout 是**纯函数**（输入树、宽度、主题）；
- renderer 是**绘制投影**；
- editor 是**有状态的文本服务**；
- workspace 是**有状态的工作区服务**；
- commands 是**调度层**；
- views 是**投影 + 命中**。

它们通过明确的契约连接，而不是共享一个万能接口。

## 8. 新功能怎么放进模型

每次加功能，先按顺序问：

1. **新实体？** 文档/仓库/标签/索引/浮层？→ 进 Domain，写归属和生命周期。
2. **新用户意图？** 打开/返回/重命名/跳转？→ 进 Command 表，不先想键。
3. **新焦点层？** 它是整页、浮层、文本焦点还是模态？→ 进 Focus 栈，定优先级。
4. **新用户取舍？** 主题/启动/键位？→ 进 Preference schema，标 apply 时机。
5. **新外部资源？** 文件系统、索引、导出进程？→ 建 Service，定义 effect 和失败模式。
6. **都不符合？** 那它大概率应该扩展现有模块，而不是新建。

然后填六张表：不变量、归属、命令、焦点、转换、失败。每张不超过 10 行。

## 9. 和现有代码的对应

| 现有代码 | 在模型里的位置 | 迁移建议 |
| --- | --- | --- |
| `app.h` | 组合根 + 共享状态 | 不再堆新业务；把状态按归属拆出去 |
| `input.cpp` | 平台输入 + 旧路由器 | 逐步变成“事件 → 焦点 → 命令”的薄路由器 |
| `keymap.*` | 命令绑定的雏形 | 扩展成 `CommandId + KeyChord + Context` |
| `home_logic.*` | Workspace 纯逻辑 | 扩展成 WorkspaceState，继续用 pending/effect |
| `dirmodel` / `repos` | Workspace 的纯数据 | 保持无 Win32，继续单测 |
| `workspace_index.*` | Index Service | scan 在 worker；query/排序保持纯函数 |
| `homeview.cpp` | Workspace 的薄壳 | 只画 + 命中 + 执行 effect |
| `startpage.cpp` | 空文档槽位的视图 | 和 Home 共用 WorkspaceState |
| `tabs.cpp` | 文档集合 | 不解析、不渲染、不拥有仓库 |
| `settings.*` | 偏好存储 | 加 schema/validate/apply timing |
| `overlays.cpp` | 浮层视图 | 抽公共的 overlay 优先级接口（第三个浮层后再做） |
| `markdown/render/editor` | 文档流水线 | 保持契约，不让工作区逻辑渗进去 |

## 10. 一页纸的愿景模板

如果你只想先写一页，写这些：

```text
# Tinta
一句话：
为谁：
不做什么：
三条硬不变量：
五条原则（按优先级）：
三个最重要的取舍：
一个用户典型场景：
一个明确拒绝的功能：
```

这页纸比架构图更能决定后面的模块边界。架构图会变，宪法尽量少变。
